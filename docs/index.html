1Introduction

The PCARDIO API gives developers access to the full capability of the PCARDIO recorder. It lets you integrate sensor data such as ECG, bioimpedance, EMG and IMU motion into your own applications, configure sensor settings, and manage recorded data. The platform is used in medical research, sports science, occupational health and defence applications.

Whether you are building a mobile app, an IoT solution or any other software that needs connectivity and data exchange with the recorder, this reference provides the information required to reach every function of the PCARDIO recorder.

A PCARDIO recorder can be reached over two communication protocols: wireless BLE, and serial communication through a micro-USB connector. The wireless BLE link provides access to the Core Interface, which covers device configuration and data access. The serial link provides access to the Serial Interface, which extends the Core Interface. In addition, the recorder exposes a USB mass storage interface that allows you to configure the recorder and download data as files.

This document explains how to:

  • Discover and communicate with a PCARDIO recorder over wireless BLE and serial communication
  • Understand the structure of the files in the recorder's mass storage
  • Configure device and measurement settings
  • Interact with the recorder's internal memory map
  • Parse the data streamed or logged by the PCARDIO recorder
Firmware

This reference applies to recorder firmware v1.1.2 or higher.

Wireless BLE

Nordic UART Service, Core Interface packets, live streaming of raw or derived signals.

USB serial

ASCII-framed Core Interface, plus firmware upgrade and reboot commands.

USB mass storage

Configure through config.txt and download recordings as files, with no protocol code.

Working code for everything described here is available in the PCARDIO-Examples repository, and the recorder models themselves are listed on the ECG recorders page.

2Communication protocols

To exchange data with a PCARDIO recorder you first establish a connection over one of the available communication protocols. The interfaces can only be used once that connection exists. Each protocol has its own characteristics, described below.

2.1BLE communication

The PCARDIO recorder communicates over wireless BLE using the Nordic UART Service (NUS), a custom BLE service that emulates a serial port.

The recorder exposes a single GATT service. In BLE, the GATT protocol organises data into services, each service groups related characteristics, and characteristics are the readable, writable or notifiable values that form the interface for data exchange. The PCARDIO service is identified by the 128-bit UUID 6E400001-B5A3-F393-E0A9-E50E24DCCA9E, which is required to discover and connect to the recorder's custom NUS implementation.

Within this service, PCARDIO defines two characteristics. Notifications must be explicitly enabled on the TX characteristic before the recorder can send messages.

Table 1. BLE characteristics
CharacteristicUUIDProperties
RX characteristic6E400002-B5A3-F393-E0A9-E50E24DCCA9EWrite, write without response
TX characteristic6E400003-B5A3-F393-E0A9-E50E24DCCA9ENotify

When scanning for BLE devices, your application receives two kinds of packet: the advertisement packet and the scan response packet. Both are broadcast by nearby devices and carry metadata that identifies them before a connection is made. The PCARDIO recorder sends a custom advertisement that includes the device name PCardio. The scan response packet includes the service UUID, which identifies support for the Nordic UART Service.

The recorder uses the 2 Mbps PHY introduced in BLE 5.0. To take full advantage of this throughput and to ensure compatibility, use BLE 5.0 or higher on the central device.

Three BLE parameters matter for performance:

  • Connection interval — how often the peripheral and central exchange data. It ranges from 7.5 milliseconds to 4 seconds in 1.25 millisecond increments. The actual limits vary by operating system and BLE stack.
  • ATT MTU — the maximum size of each GATT packet. A larger MTU reduces the overhead for large messages.
  • Data Length Extension (DLE) — expands the payload beyond the default 27-byte BLE packet limit.

Maximising both ATT MTU and DLE helps ensure that most Core Interface requests fit in a single BLE transaction, which improves throughput and reduces latency. More on live streaming is available on the real-time biosignal streaming page.

3Core interface

The Core Interface gives direct access to the recorder's memory through four packet types, designed to make reading and writing memory blocks straightforward. A packet is built from four fields:

  • Opcode — a single byte that specifies the packet type.
  • Address — a 32-bit unsigned integer giving the starting memory address of the read or write operation.
  • Length — a 16-bit unsigned integer giving how many bytes to read or write.
  • Data — a byte array containing the payload: either data read from the recorder, or data to be written to it.

Byte order

All multi-byte fields in the packets use little-endian format. The examples below show how values are encoded.

Fragmentation

Large Core Interface messages may be split across several smaller transport packets because of protocol size limits. Your application should concatenate the fragments and wait until the entire message has arrived before parsing it.

One operation at a time

The PCARDIO recorder supports only one operation at a time. Always wait for the current data transaction to complete before starting a new one, and avoid sending read or write packets while the recorder is streaming: doing so can cause communication issues or data loss.

3.1Read packet

Read packets request a specific number of bytes from a given memory address. Use them to retrieve fixed blocks of data.

Table 4. Read packet: read 4 bytes from memory address 16
0123456
0x010x100x000x000x000x040x00

3.2Data packet

Data packets write data to the recorder, overriding part of its memory. The recorder also sends data packets as responses to read or stream requests, carrying the requested payload.

Table 5. Data packet: write the value 1 to a 32-bit register at address 16
012345678910
0x020x100x000x000x000x040x000x010x000x000x00

3.3Abort packet

Abort packets are single-byte commands that interrupt any ongoing data streaming. Use an abort packet to stop a continuous stream from the recorder immediately.

3.4Stream packet

Stream packets request continuous data streaming. Unlike read packets, they cause the recorder to keep sending new data as it becomes available. Streaming is restricted to a specific region of the recorder's memory, the stream memory.

Table 6. Stream packet requesting 237 bytes
0123456
0x040x000x000x000x100xED0x00

The address bytes 00 00 00 10 decode little-endian to 0x10000000, which is 268435456, the start of the stream memory.

4Serial interface

The Serial Interface carries the Core Interface over the serial connection, wrapping each Core Interface packet in an ASCII-encoded message. Besides the Core Interface packet, two additional packet types can be sent. Serial Interface messages have the following structure:

  • Prefix — a dollar character $ (0x24) marking the start of the packet.
  • Opcode — a single character indicating the Serial Interface packet type.
  • Data — the encapsulated Core Interface packet as a hex-encoded byte array. Every byte is two characters in the range 0–9 or A–F. The first two characters represent the first byte, the third and fourth the second byte, and so on.
  • Postfix — a line feed \n (0x0A) marking the end of the packet.
Table 7. Packet fields and byte order of the Serial Interface packets

5.3Measuring configuration memory

Registers that determine the state and configuration of the measurement.

5.3.1User id

Space for up to 12 characters identifying who the data belongs to.

Privacy

The recorder does not encrypt the value written to the user id register. Do not write names or other confidential information in plain text; encrypt the value before writing it to the recorder.

5.3.2Start time

Schedules the Unix time in seconds at which the recording should start. Logging starts automatically as soon as the time register exceeds this value.

5.3.3Stop time

Schedules the Unix time in seconds at which the recording should stop. Logging stops automatically as soon as the time register exceeds this value.

5.3.4Sampling configuration

Holds the configuration used for the measurement: which sensors are enabled, and their gain, sample rate and data type. See sampling configuration for the structure of this register.

5.4Stream memory

Holds the most recent data packet to be streamed. The length of a data packet depends on the sampling configuration; the maximum size is 16384 bytes. The format and parsing of these packets is described in data packet.

6.1.1Time

Unix time in seconds of the last sample in the buffer.

6.1.2Ticks

The number of elapsed ticks from a 32.768 kHz clock that must be added to the timestamp. Since that clock produces 32,768 ticks per second, convert the value to standard ticks of 100-nanosecond intervals by multiplying by 10,000,000 / 32,768.

6.2Payload

The payload contains the data from every enabled sensor. The order and size of each sensor data block is determined by its sample rate, data type and position in the sampling configuration. See sampling configuration for a worked example.

7Sampling configuration

The PCARDIO recorder offers extensive customisation so that a measurement can be tailored precisely to its purpose. Four aspects are under your control:

  • Sensor selection — choose which sensors are active, based on the data each use case requires.
  • Gain adjustment — set individual gain levels per sensor to keep data accurate and optimise the signal-to-noise ratio.
  • Sample rate configuration — define the sample rate per sensor to balance resolution against resource use.
  • Data type customisation — choose the data format that suits the application, optimising for storage or precision.

This flexibility makes the recorder adaptable across scenarios, from precise diagnostics to research applications that need tailored data collection. The full range of signals the platform supports is described on the sensors and signals page.

The configuration is set by writing the 68-byte sampling configuration register. The register holds a 32-bit unsigned integer giving the number of enabled sensors, followed by an array of up to 16 sensor configurations.

Converting digital samples to physical values

The general formula to convert a digital value to its analog equivalent is:

value_A = ( (max_A - min_A) / (max_D - min_D) * (value_D - max_D) + max_A ) / gain

where the subscripts A and D mean analog and digital respectively.

Example

For a sensor gain of 8 and a default analog range of ±16, the actual range becomes ±2.

Calculating the data packet size

Because the recorder is optimised for throughput, the sampling configuration determines the size of the data packets. The pseudocode below calculates the packet size and the start index of each enabled sensor's data.

packet_size = 13
for i = 0 to count do
    start_address[i] = packet_size
    packet_size += sensors[i].data_type.total_size * (sensors[i].sample_rate / 5)
Why divide by five

The sample rate is divided by 5 because the PCARDIO recorder produces five data packets per second. The total size for each data type is in table 30.

Worked example

Suppose the accelerometer, the button marker and the battery level are enabled, in that order:

  • Accelerometer — 50 Hz sample rate, measured in G
  • Button marker — 5 Hz sample rate, default unitless data type
  • Battery level — 5 Hz sample rate, measured as a percentage

8File interface

When the recorder is connected through the docking station, the file interface becomes available. It lets you set the recorder and measurement configuration and access recorded data as ordinary files. Three files are present: config.txt, data_YYYYMMddHHmmss.txt and log.txt.

8.1Configuration file

config.txt contains part of the info memory, the recorder configuration memory and the measurement configuration memory. It has a fixed length of 144 bytes and is required for the recorder to work.

Required file

If config.txt is missing the recorder enters an error state, and returns to normal operation only once the file is restored.

Editing this file has the same effect as changing the memory registers over wireless BLE. The new configuration is read when the recorder is disconnected from the docking station. The prefix and postfix hold fixed values.

8.2Data files

When the recorder logs data it creates a file named data_ followed by the file creation date as YYYYMMddHHmmss:

  • YYYY — the year
  • MM — the month
  • dd — the day
  • HH — the hours, from 0 to 24
  • mm — the minutes
  • ss — the seconds

A data file has a maximum length of 512 MB. When it reaches that size the recorder closes it and creates a new file to continue logging into. A new file is also created every time the recorder is reset, so a recording interrupted by charging is split into at least two files: one before charging and one after.

The header of a data file holds a copy of the configuration file, followed by the start and stop time of the file. The rest of the file is a sequence of data packets. Use the sampling configuration from the file header when parsing them.

Table 35. Structure of the data files

Housekeeping

Remove the data files from the recorder once they have been copied to local disk, so that the recorder's memory does not fill up.

8.3Log file

The log file is generated automatically. The recorder writes information to it that helps diagnose unexpected behaviour. Copy this file when downloading data and then remove it, so that it does not grow large.

9Input error handling

Reading or writing device memory can result in an invalid operation. When that happens the recorder ignores the instruction and reports the problem by updating the input error code and timestamp registers. Five error types can be reported:

  • Read-only error — writing to a read-only register.
  • Invalid address — the address field is outside the memory map.
  • Invalid length — the length is bigger than the memory.
  • Invalid data — the data contains invalid values for one of the registers being written.
  • Invalid state — the measurement configuration was modified while the recorder is logging data.

10Good practices

10.1Reading and writing multiple fields

Reading from and writing to device memory can be done in larger blocks that span several fields of the memory map. Note that a number of memory locations require the pin to have been written before reading or writing is allowed.

10.2Single operations

The recorder handles a single operation at a time. Wait for a data transaction to complete before starting a new one. Every packet sent to the recorder results in one or more packets sent back, and those returned packets can be used to trigger the next transaction. Avoid sending read or data packets while the recorder is streaming: send an abort packet, perform the read or write operations you need, then restart the stream.

10.3Battery and data size monitoring

Read the battery level and the size of the data file frequently, to avoid reaching a low-power or full-storage state.

In low-power mode the recorder stops responding, and you need to wait until the battery has charged enough before using it again. With no storage left, the recorder will not start a recording, or will stop one that is in progress.

10.4Quick start

The diagram below shows the steps to set up and record a measurement.

The first step after connecting is to write to the pin register. Next, make sure the recorder's time is accurate; this matters most when scheduling a measurement, and the time register should be updated whenever it differs from the host clock by more than one second. To schedule a measurement, change the measurement configuration either by editing config.txt or by updating the measurement configuration registers over wireless BLE. Once the measurement is finished and the data downloaded, leave only config.txt on the recorder so that its memory does not fill up.

A runnable version of this sequence is in the Python examples, and a step-by-step walkthrough is on the quick start page.
